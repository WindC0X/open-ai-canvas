## 一、持久化纪律（跨重启不丢）

### D1 ★ 跨重启产出必须落仓库侧

**规则**：任何跨会话存活期超过一次机器重启的产出，**必须提交到仓库**（或仓库侧 `.trellis/workspace/<dev>/`），
不得只留在 `/tmp`。

**判据**：问自己「机器重启后，这条产出还能被谁找到？」
- 若答案是「只有我记得」→ **必须落盘**
- 若答案是「/tmp 里」→ **必须落盘**（/tmp 清空是常态）

**事故记录**（2026-10-05 一天内三次）：

| # | 丢失物 | 后果 |
|---|---|---|
| 1 | A线 20 条 R1+R2 修复队列（`/tmp/rider-queue-r1-fix.md`） | 队列需从会话消息重建，重建后落 `queues/r1-r2-fix-queue.md` |
| 2 | 评审线 R1 报告原文（`/tmp/review-r1.md` + `/tmp/review-r1/agents/batch-F.md`） | **F-1 修复无法执行**——只剩 journal 级摘要（「归属修正」+ 两处行号），不足以定位确定性缺陷，最终降级为「登记待查」 |
| 3 | B线 T1-P1 待确认项 | 需重新询问 |

**落盘位置约定**：
- 队列 / 待办 → `.trellis/workspace/<dev>/queues/<name>.md`
- 评审报告 → 评审线**自己的分支**（`docs(review)` commit，**不推 main**，不混入 main 的开发 journal 面）；
  **但产出分支应推 fork 保全**（branch-only，见 C5）
- 任务书 → `docs/artifacts/<batch>-task-book.md`（随批提交）
- 交付报告 → 直报消息 + 关键结论入 journal

**★ 「不 push」的准确含义**（2026-10-05 评审线指出矛盾后修正）：
「不 push」指的是**不推 main、不推会被当作发布物的分支**，
**不是「不推任何远端」**。

理由：若分支只在本地 → 仓库损坏 / 误删 / 重建 → 报告仍会丢
（这正是 F-1 事故的同类风险，只是从 /tmp 换成了本地 git）。
⇒ **产出分支可且应推 fork 保全（branch-only，绝不合入 main）**。

反面案例：控制线 2026-10-05 曾令评审线「把 review/w5-batches 推 fork」，
与该文件 D1/C5 原文的「不 push」字面矛盾——**矛盾在文档，不在令**：
「不 push」本意是「不混入 main」，而非「不得离开本地磁盘」。

**★ 评审报告的特别要求**：报告**正文**必须落盘（分支或 docs/），
不得只留摘要。F-1 的教训正是「摘要够不着缺陷」——
摘要能说明「有个不一致」，但定位不了「哪个不一致」，导致修复线只能空转或猜。

## 二、git 纪律

### G1 ★ 合并 commit 的文件面：用 `git diff <merge>^1 <merge>`，不用 `git show`

**规则**：取合并 commit 的完整改动面，一律用：

```bash
git diff --name-only <merge>^1 <merge>      # 对第一双亲
git show -m <merge>                          # 等价（逐双亲）
```

**禁用**：`git show --name-only <merge>` —— 它只返回**合并自身的冲突解决面**，
读不到被合入分支的改动。

**事故记录**（一天内两次）：

| 线 | 对象 | `git show` 口径 | 正确口径 |
|---|---|---|---|
| B线 | 预检 sync merge | 13 文件 | **341 文件** |
| A线 | 门禁 eslint 文件列表 | 2 文件 | **16 文件**（漏 14 个本批核心文件） |

**★ 派生防线**（真正让脚本自己暴露问题）：

```bash
mapfile -t FILES < <(git diff --name-only "${MERGE}^1" "$MERGE" | grep -E '^web/.*\.(ts|tsx)$' | sed 's|^web/||')
echo "文件数: ${#FILES[@]}" >&2                      # ← 数组计数，空输入显性为 0
[ ${#FILES[@]} -eq 0 ] && { echo "❌ 文件面为空，中止" >&2; exit 1; }
bunx eslint "${FILES[@]}"
```

⚠️ **不要用 `echo "$FILES" | wc -l` 计数**（2026-10-05 B线 实测发现）：
`echo` 即使变量为空也会输出一个换行符，`wc -l` 数的是**行数**而非**元素数**，
空输入 = **1 行**（实测：`FILES=""; echo "$FILES" | wc -l` → `1`）。

**后果**：`[ -z "$FILES" ]` 仍能拦住（判据正确），但**显性打印失效**——
读者看到「文件数: 1」会以为真检了 1 个文件，
与 A线 那次「输入实为 0 个文件、退出 0 但什么都没检」的盲区**同形**。

最小修法：`printf '%s' "$FILES" | grep -c .`（不用 `echo`）；
推荐修法：用数组 `mapfile -t` + `${#FILES[@]}`（还顺便正确处理含空格的文件名）。

**★ 场景区分**（B线 补充）：若该脚本用于 **lint/格式化**输入，需加 `--diff-filter=ACMR`
（排除已删除项；实测 `e4be6253` 全量 341 文件 → lint 口径 336），
否则 lint 会拿到已不存在的文件路径。
⇒ 工具脚本 `scripts/merge-file-face.sh` 已按此实现（`--exclude-deleted` 开关，B线）。

### G2 ★ 分支归属判定：用 merge-base 或 merge-tree，不用两点 diff

**规则**：判断「某分支是否会回退他线修复」时：

```bash
git diff --name-only $(git merge-base main <branch>) <branch>   # 对合并基点
git merge-tree --write-tree main <branch>                        # 干跑（推荐）
```

**禁用**：`git diff main <branch>` —— 两点 diff 只描述「两棵树的差异」，
不描述「任一侧做了什么」。分支基点早于 main 的合入时，main 的增量会呈现为
「分支的删除」。

**事故记录**：B线 首次 T1-P1 登记误报「`7db3fa10` 会静默回退 R1 修复」——
它读的是 `git diff main 7db3fa10`；真实 merge-tree 干跑零冲突，R1 修复完整存活。

**注意**：merge-tree 是内容寻址的，main 推进后重跑返回不同 tree hash
（B线 得 `2964ad51`，控制线得 `369ab971`）——**结论一致即可，无需对账**。

### G3 ★ 跨枝写入必须绑定目标分支的当前基线

**规则**：往某分支写内容（journal、队列、文档）前，**重新测量该分支的当前状态**，
不得使用先前观察到的数字。

**事故记录**：
- A线 journal 落 main：控制线记录 main = 1527 行，A线 实测 **1552 行**
  （差 25 行 = B线 在测量后追加）→ 若按旧数字落盘，会漏掉那 25 行
- A线 另一次：journal commit `21a77bcb` 落在**批分支**上且基于**旧基线**（1284 行 vs main 1527 行），
  合并会**回退他线三次追加** → 拦下，`git reset --hard` 修正

**纪律推论**：**journal 一律落 main，不落批分支**。
理由：① 批分支可能被拒（journal 白落）② 同区域追加会回退他线内容。
（B线 在批分支加 journal commit 本次未回退，因它是**纯追加**（不同区域自动合并）——
但这是运气，不是设计。）

### G4 ★ 操作前核归属

**规则**：
- `git checkout <branch>` 前 → `git worktree list` 确认该分支**未被其他 worktree 占用**
- `git push` 前 → `git ls-remote <remote> <branch>` 确认本地 tip 与远端一致

**事故记录**：A线 无法 checkout main（被 B线 worktree 占用），declined to disturb；
B线 两次在 main 上做登记提交后未及时释放，造成 A线 落盘受阻。

### G4.1 ★ 控制线不得在多线共享仓库直接 commit（含 index.lock 竞态）

**规则**：任何线（尤其控制线）在**多线共享的同一仓库工作树**做 git 写操作前，
必须先确认**无其他线正在该工作树执行 git 写操作**。

**推荐做法**：**控制线使用自己的独立工作树**（`/home/windc0x/oac-ext4/oac-wt-ctrl`，
branch `ctrl/docs`）做文档/纪律类提交，不在主仓工作树操作——
主仓工作树是 **A线 的家**（它负责 main 面合入），控制线在其中提交即侵入他线家域。

**事故记录**（2026-10-05）：控制线在**未通知**的情况下于主仓工作树（= A线 的家）
执行 `git add -f docs/artifacts/... && git commit && git push`（pid 392349），
恰好与 A线 的 journal commit 撞上 `.git/index.lock`：
```
fatal: Unable to create '/mnt/f/CODE/Project/open-ai-canvas/.git/index.lock': File exists
```
**A线 处置正确**（按纪律未干扰）：等待 30 秒至控制线完成，未删 lock、未强杀，
随后核实控制线提交落于其合并之上、无冲突，自身 journal 改动完好，commit/push 成功。

**无损失是运气**：若两线**同时**进入 index 写操作，或控制线跑的是 `git reset` /
`git checkout -f` 这类破坏性命令，后果会严重得多。
⇒ **`index.lock` 是真实的并发风险点**，不能靠「撞上了再等」解决。

**★ 等待策略的边界**：`index.lock` 冲突时「等待对方完成」**只适用于无破坏性的
add/commit**。若冲突方在跑 `reset` / `checkout -f` / `rebase` / `filter-branch`，
**必须停止操作并上报**，不得盲目等待——对方可能正在改变你依赖的状态。

**★ G4.1 第 2 实例（2026-10-05，控制线自犯，A线 诊断）**：
控制线向 A线 下达合并令后，**未确认 A线 是否已开始执行**，
就在同一 worktree 的 `main` 上提交了一条纪律文档（`01d3997c`）。

**reflog 实证**（时间线可复原）：
```
19:04:04  A线  checkout main（HEAD = 81bf61e6）
19:04:52  控制线 commit 01d3997c   ← ★ 在 A线 已 checkout 之后写入 main
19:06:29  A线  merge 成功（起点已变为 01d3997c）
```
**A线 报的现象**：`git merge --no-ff` 返回 `fatal: stash failed`
（A线 当时 HEAD = 81bf61e6，而 main 已被推进到 01d3997c）。

**⇒ 根因**：控制线在**对方已 checkout 的工作树**上写入提交 ——
与第 1 实例（index.lock 竞态）**同族**，但形态不同：

| | 第 1 实例 | 第 2 实例 |
|---|---|---|
| 形态 | 两线**同时** add/commit ⇒ `index.lock` 冲突 | 一线 **checkout 后**另一线写入 ⇒ `stash failed` |
| 检测 | git 报 `index.lock` 存在 | git 报 `fatal: stash failed`（**误导性信息**） |
| 修复 | 等待 + 重试 | 确认状态干净后重试 |

**★ 为什么第 2 实例更隐蔽**：`stash failed` 的字面意思是「暂存失败」，
**不提示「main 被他人推进」** —— 若不看 reflog，很容易误判为 git 内部故障。

**★ 纪律**：
> **下达合并令后，控制线不得在同一 worktree 的该分支上做任何写操作**，
> 直到对方报告合并完成。若必须落盘，**改用其他 worktree**（如 `~/oac-ext4/oac-wt-baseline`）。

**★ 控制线自评**：这是当日**第四次自犯**，且与第 1-3 次同源
（**操作前未核实对方状态**）：
| # | 自犯 | 纪律 |
|---|---|---|
| 1 | 注释红数漏版本基准 | V7 附2 |
| 2 | 引用未合并分支漏标分支 | V7 附2-a |
| 3 | 读部分输出就下结论 | C1 附 |
| 4 | **下达合并令后写入对方 main** | **G4.1 第 2 实例** |
**⇒ 四次根因完全一致：操作前未核实对方状态。**

**★ G4.1 附：共享工作树的 main 是「单写者资源」**（A线 2026-10-05 提出，控制线采纳）

**规则**：**同一时刻只应有一线在某个工作树的 main 上写**
（`checkout` / `commit` / `merge` / `push` 均算）。
其他线需要写 main 时，走**独立 worktree + push**，或等对方报告完成。

**为什么比「写前确认」更强**：
| 方案 | 依赖 | 失效条件 |
|---|---|---|
| 写前确认对方状态 | 对方**诚实报告**状态 | 对方未报告/报告滞后/双方同时确认 |
| **单写者 + 独立 worktree** | **结构性隔离** | 无（物理上不共享工作树） |

**⇒ 与 A线 注入层的设计同源**：
> **让误用不可能 > 靠约定** ——
> 注入层「只接受已定序的计数」（不猜语义）↔ 单写者「只在独立 worktree 写」（不抢 main）

**★ A线 补的一条关键事实**：**失败操作不留 reflog**
```
reflog 只记录成功变更（HEAD 移动）。
失败的 merge（因 stash failed 中止）不移动 HEAD ⇒ 【无条目】
⇒ 若当事人不当场报告，该并发事故【事后无法从 reflog 复原】
```
**⇒ 这与 C1 附（读脚本输出必须读到汇总判定行）同族**：
**失败必须被读到，否则不可复原** ——
reflog 会「静默丢失」失败操作，正如脚本的汇总判定行会被漏读。

**★ 两次事故的运气成分（A线 指出）**：
两次（`index.lock` 冲突 / `stash failed`）都发生在**无破坏性操作**下：
- 第 1 次：控制线跑 `add/commit`（追加式）
- 第 2 次：A线 跑 `merge --no-ff`（失败即中止，不改状态）
**⇒ 若任一方跑的是 `reset --hard` / `checkout -f`，后果不可逆。**
**⇒ 不能因「两次都没损失」而降低该纪律的优先级。**

**★ 附2：失败报告必须附「失败命令 + 时间戳」**（测试线 2026-10-05 提出，控制线采纳）

**规则**：报告 git/工具失败时，**必须同时给出失败命令原文与发生时间**。

**为什么**（测试线 的精确化，比 C1 附更强）：
| | 现象 | 后果 |
|---|---|---|
| **C1 附** | 输出**有**失败信息，但读者没读到 | 当事人**能**事后补救（信息还在） |
| **失败不留 reflog** | 失败**没有留下任何痕迹** | 当事人**不当场报告就永久丢失** |

**⇒ 后者更严重**：它把「事后可复原」变成「**当场不报即永久丢失**」。
**结构性预防在此处不可用**（无痕迹可查）⇒ **唯一防线是当场报告**。

**实例（2026-10-05，A线 的处置正确）**：
A线 的 merge 失败（`fatal: stash failed`）**当场报告了**，
控制线才能用 reflog 复原**控制线 commit 的时间线**（19:04:52）——
**若 A线 没报，控制线的那次写入就无从定位**（因为失败本身不留痕）。

**★ 为什么需要【时间戳】**：reflog 复原需要**时间锚点** ——
只说「merge 失败了」无法定位到「哪个时间窗口」；
报「`fatal: stash failed` @ 19:05 左右」才能与 reflog 条目对齐。

**⇒ 可执行动作**：
```
失败报告 = 失败命令原文 + 发生时间（精确到分钟）+ 当时的 HEAD/branch
```

**★ 与「表述强度」族的关系**：本附条属**观测族**（§四·五）——
失败信息若不携带产生条件（时间），则**不可复原**，与「红数须附注入点」同理。

**★ 附3：交付/验收的 git 状态三检查**（2026-10-05，B线 发现 + 控制线验收侧漏检）

**背景**：B线 在 `detached HEAD` 上 commit 后**未更新分支引用**，
交付报告写「分支 `test/f09-channel-gate` @ `bbf0e2d9`」，
但该分支**实际仍指向起点 `28d1e46e`**（reflog 证实：创建后从未移动）。

**⇒ 两侧都要检查（缺一不可）**：

| 侧 | 检查项 |
|---|---|
| **生产侧**（交付方） | `git branch --show-current` **非 detached**；`git rev-parse <branch>` = 交付 commit |
| **验收侧**（接收方） | ① `ls-files`/`ls-tree`（**内容**）② `rev-parse <branch>`（**引用**）③ HEAD 是否为 detached |

**★ 关键信号**：`git rev-parse --abbrev-ref HEAD` **返回 `HEAD`** ⇒ 处于 detached ⇒
**「分支 @ commit」的表述不成立**（内容对但引用未更新）。

**★ 控制线自评（验收侧漏检）**：验收时执行了
`git rev-parse --abbrev-ref HEAD` → **返回 `HEAD`**，
但**未警觉**该信号 ⇒ 只核实了「工作区有这些文件」，
**未核实「分支指向该 commit」** ⇒ **验收断言覆盖不全**（V9 ①-a 形态）。

**★ 与 V7 附2 的关系**：V7 附2 是「**生产侧标基准 + 审查侧核基准**」；
本附条是同一结构在 **git 状态**维度的实例 —— **两侧缺一不可**：
- 只做生产侧 ⇒ 验收方仍可能漏检（本次控制线）
- 只做验收侧 ⇒ 生产方仍可能交付错误形态

**★ 一般化**：
> 任何「**A 指向 B**」的交付形态（分支→commit、标签→commit、指针→对象），
> **交付方与验收方都必须显式验证该指向**，不能只看内容存在。

### G7 ★ 冻结期内的自主判断：先报一句，再动

**背景**：批次交付后进入「冻结待合」（不再追加 commit，防止已交付待审的对象被悄悄改变）。
但实际会出现「冻结期间发现必须补的东西」的情况。

**规则**：
- **判断权可以下放**：控制线若说「你判断是否补」，则你**有权决定补或不补**
- **但时序上先报一句**（含四要素）：
  1. 要补什么
  2. **为何必须现在补**（不补的后果）
  3. **用新 commit 而非 amend**（保持已绑定的验证 hash 有效）
  4. 是否影响已绑定的验证结果 / 是否已被其他线引用
- **等确认或超时（约 5 分钟无回应）后自行执行**

**为何要报**：不是因为不信任判断，而是**控制线可能掌握你不知道的上下文**：
- 若控制线正准备把该分支合入，你的新 commit 会与合入操作撞车
- 若有另一线正基于旧 tip 写引用代码，tip 变更需通知它
- 若你改了行为却以为是注释，报一句就能被拦下

**不等确认硬等 = 浪费；不报直接动 = 失去控制线的全局视野。**

**正面案例**（B线 2026-10-05，`2ec6d12b`）：发现 `merge-file-face.sh` 的
SCOPE 剥前缀契约只存在于调用示例、未写进脚本（从仓库根消费会全找不到文件，
且**这不是空输入**、空输入防线拦不住），判断现在补成本最低。
**其做法有三处值得表扬**：
- **用新 commit 而非 amend** —— 意识到 amend 会让「控制线独立复跑的四项数字」失去对象
  （绑定的 hash 变了），而新 commit 只加契约不改行为 ⇒ **旧验证仍有效**
  （G5 的正确应用——不但守纪律，还守它的精神）
- **把反例写进注释**（不只写正例）—— 反例更能防止误用
- **主动说明「我打破了冻结」并请求约束**
**唯一可改进**：报告在动之后而非动之前（时序）。

**负面模式**（警戒）：若改动**实际改变了行为**、**amend 了已绑定的 commit**、
或**已被其他线引用**，则**不得自主执行**，必须等确认。

## 三、验证纪律

### V1 ★ 验证形态必须匹配被验证对象

**规则**：测试手段必须触及真实对象，不得用「近似物」代替。

**事故记录**：
- b12r17 的 GO 漏掉 E-1（毕业门控失效），因为它只测了「更多-menu」面，
  没测**图片节点工具栏**路径
- F-3「size 修复贯通」是**测试镜像实现**——测试自己算好 size 传入，
  真接线在 `use-canvas-media-tools.ts:1572-1576`，测试从未经过它
- 合并 commit 必须**自身可编译**——ritual 验收只看了工作树，没看提交对象，
  导致 `9c3ef6c8` 的解析错误连过三个 commit

### V2 ★ 可证伪性：注入缺陷必须红

**规则**：每个护栏/修复测试必须证明可证伪——**注入缺陷 → 测试必须失败 → 恢复**。
不能对注入的缺陷失败的测试，什么也没验证。

**做法**：断言**真实生产接缝**（提取为函数），而非镜像实现表达式。
（B线 的 `review-r1-wiring.test.ts` 在评审线批评后从镜像表达式自纠为断言
`filterToolsForGuide` / `badgeCenter` / `resolveLinearFlowConfig` / `resolveLinearFlowModel` 的返回值。）

**测试形态优先级**：行为级断言 > 源码文本断言。
文本断言（`Bun.file(...).text()` + `toContain`）仅作兜底，不作主证。

### V3 ★ 结论必须绑定被验证对象的版本

**规则**：任何「已验证」结论必须记录**验证对象的 commit**，以及**环境版本**。

**事故记录**（B线 2026-10-05）：旧后端进程（04:39 启动）不含统一任务面批的后端改动
（`4d535b57` 的 `user_data_page.go` workspaceType 透出），列表 API 一度返回空字段，
**差点误判为缺陷**。
⇒ **凡在旧进程上验证跨批功能，须先确认进程启动时间晚于相关 commit。**

#### ★ V3 附：归因表述三要素（谁发现 / 谁修复 / 绑定哪个 commit）

**规则**：跨线报告或环境基线中写「某问题已修 / 某数字为 N」时，必须**同时**给出：
1. **谁发现**（现象来源）
2. **谁修复**（修复落盘的 commit）
3. **结论绑定哪个 commit**（数字在哪个版本上测得、由谁测得）

**由来（2026-10-05 活例）**：测试线在 ENV-BASELINE 坑7 写
「**现已修**：探针 `selfCheck()` 自行清理…并加证伪测试（移除清理代码 ⇒ **2 fail**）」。
控制线核验发现**三重问题**：
| # | 问题 | 实情 |
|---|---|---|
| 1 | **他方测量被写成己方** | 「2 fail」是**控制线**的实测，测试线是**读控制线终端**看到的 |
| 2 | **未绑定版本** | 控制线测的是 `164c6893`；测试线的树是 `2aa59215`（**不含修法2**）⇒ 该数字在其树上不可复现 |
| 3 | **时态误导** | 写「现已修」（完成态），但测试线的树**没有该修复** |

**测试线自查后的修正**（`09cf7f7`）——**正面范例**：
> | 修复 commit | `164c6893`（控制线落盘）—— 本 ENV-BASELINE 版本 `4b363b9` **尚未含** |
> | **测试线独立实测** | 在 `9b4c8b85`（含修复）上：基线 11 pass / 注入 → 2 fail / 恢复 → 11 pass |
> ★ **归因声明**：现象由测试线独立发现（控制线亦独立复现）；修复由控制线落盘 `164c6893`；
> 上表实测数字由**测试线在 `9b4c8b85` 上自测**，不是引用他方声称。

**为什么这条与 V3 同族但需单列**：V3 管的是**结论**（「我验证了 X」必须附版本）；
本附条管的是**归属**（「X 已修 / 数字是 N」必须附**谁**在**哪个版本**上得出）。
**归属错位时，结论本身可能是对的** —— 但读者会把「他方声称」当成「已验证事实」。

**与 V7 附2 的关系**：V7 附2 管**行号**引用须附 commit 基准；本附条管**结论/归属**须附版本。
两者同源：**证据必须绑定其产生的条件**（同族还有 C7、V9 的「红数须附注入方式」）。

#### ★ V4 附1：flaky 检出率 —— 「跑 N 次全绿」不等于「无 flaky」（测试线 2026-10-05 实测）

**实测数据**（测试线 在 `f88fc24a` 上）：
```
第 1 次全量跑: 3124 pass / 1 fail    ← 抓到 flaky
第 2 次全量跑: 3125 pass / 0 fail
连跑 5 次:  1 红 / 4 绿
连跑 10 次: 第 1 次红 → 抓到名字
⇒ 复现率 ≈ 14%（14 跑 2 红）
```
**该 flaky 的历史复现率**：源码注释自述「全量 3 跑 1 现」（≈33%）；
V4 登记「评审线高负载 6 跑 2 红 / 控制线空闲 7 跑 0 红」——**随系统负载变化**。

**纪律**：
> **「跑 2 次全绿」对 ~14% 复现率的 flaky，检出率仅约 `1-(1-0.14)² ≈ 26%`** ——
> 即**约 3/4 概率漏检**。低频 flaky 需要**连续跑 N 次**（或长时压测）才有足够检出率。
> **报告「未出现 flaky」时必须说明跑了多少次** —— 否则该阴性结论的强度未知（与坑5 同族）。

**★ 跑数 → 检出率对照表**（p = 0.14，可直接查表判断阴性结论强度）：
| 跑数 N | 检出率 `1-(1-p)^N` | 漏检率 |
|---|---|---|
| 2 | **26%** | 74% |
| 4 | **45%** | 55% |
| 10 | **78%** | 22% |
| 16 | **91%** | 9% |

**★ 算式修正记录（2026-10-05，评审线 R11 发现 P2，控制线核实）**：
本条的初版写「检出率仅约 `(1-0.14)² ≈ 74%`」—— **算式写反了**：
`(1-p)² = 0.74` 是**漏检率**（2 次全绿的概率），**检出率是 `1-(1-p)² = 26%`**。
同句的「约 1/4 概率漏检」与「74%」**自相矛盾**（1/4 = 25% ≠ 74%），本可自证其误。

**影响不是笔误级别** —— 它会让读者**低估所需跑数约 4 倍**：
| 跑数 | 正确检出率 | 按错误数字的直觉 |
|---|---|---|
| 2 | **26%** | 74% |
| 4 | **45%** | ~93%（错误外推） |
⇒ **该纪律的核心用途正是「判断阴性结论的强度」** ——
算式写反会让审查者以为「跑 4 次就足够（93%）」，**实际 4 次只有 45%**（低于抛硬币），
**结论强度被高估一倍以上**。

**★ 本条自身即 §四·五 的实例**：**纪律正确，但支撑它的算式错误** ——
**用错数字支撑对结论**。评审线 R11 的教训二十三：
> 核验「公式/算式」时，「**结论方向正确**」不等于「**算式正确**」——
> 结论对与算式对是两件事；公式类证据**必须重算一遍**，不能因结论方向合理就跳过。

**来源说明**：测试线的原始报告（ENV-BASELINE 附1）**只写「检出力严重不足」，未给算式** ——
**该算式是控制线写入纪律文档时自行添加并写反的**（非转述错误）。

**测试线自省（正面实践）**：它指出自己 b12r23 报告写「已知 flaky 本轮 2 次跑均未出现」，
**当时那个「未出现」的证据强度比自己表述的弱** —— 主动登记。

#### ★ V4 附2：`bun test --rerun-each N` **不适用于 flaky 检测**（会制造假红）

**证据来源（★ 修正 2026-10-05，控制线自纠）**：

**测试线的观察（真证据）**：它观察到 `added Skills retries...` ×5、
`canvas audio playback` ×15 等**大量假红** ——
**这些是「确定性测试被重复执行后污染」的直接证据**（它们本不该红）。

**★ 控制线的原始「复现」不成立（自纠）**：
控制线曾报告「`--rerun-each 3` → 23 pass / 1 fail」作为佐证，
但核验后发现**观察到的 fail 是 `fallback snapshots obey the configured
minimum refresh interval`** —— 这**正是 V4 已登记的已知 flaky**
（`agent-canvas-sync.test.ts:75`），**不是状态污染的证据**：
- `--rerun-each 3` 让它跑 **3 次** ⇒ **3 倍机会命中该 flaky**（~14% × 3）
- 控制线随后重跑 5 次全绿（0/5）⇒ 复现率 1/6 ≈ 17%，**与该 flaky 的 ~14% 吻合**
- ⇒ **该观察是「flaky 被放大」，而非「同进程污染」**

**A线 独立测试也未复现**（drvfs，4 次全绿）—— 与上述判断一致。

**⇒ 教训（本条自身即 §四·五 的实例）**：
控制线把「已知 flaky 被放大」误读为「状态污染的证据」——
**证据与结论之间缺少机制核验**（V7：数字须真测；本条：**观察须与声称的机制对应**）。
`--rerun-each` 的真实缺陷是**它放大了已登记 flaky 的暴露率**，
**并可能污染其他测试**（测试线观察到的 ×5/×15）——
但**不能用「某个已知 flaky 红了」来证明后者**。

**纪律**：
> **flaky 检测必须用「多次独立进程运行」（单次连跑 N 遍）**，
> 而非 `--rerun-each`（同进程重复 ⇒ 状态污染 ⇒ 假红，会把确定性测试误判为 flaky）。
> **反向风险**：用 `--rerun-each` 得到的「红」**不能作为 flaky 证据**，
> 也不能据此把测试加进 flaky 名单。

**★ 污染源唯一性（评审线 2026-10-05 验证 + 控制线独立复现）**：

全仓 `mock.module` 共 5 个文件（@修复前），但 mock **画布 store** 的**只有 1 处**：

### V5 ★ 禁用 substring pkill

**规则**：绝不用无子串限定的 `pkill -f <pattern>`。定位端口属主 PID 用
`ss -ltnp` 或 `fuser -k PORT/tcp`；服务用 `setsid nohup` 启动并写各自日志。

**事故记录**：测试线 `pkill -f vite` 子串匹配杀掉了 A线 `:3010` 与 B线 `:3020`
的验收栈（并匹配到自己的 shell，exit 143）。
**配套纪律**：**栈归属**——非属主线不得重启他线栈，由控制线通知属主。

### V8 ★ 护栏的失败路径必须与成功路径同等可诊断

**规则**：任何护栏/守卫/校验脚本，**失败时必须能指出「哪个对象、什么原因」**；
崩溃、静默跳过、错误信息丢失，都会让护栏**被误读为护栏自身故障**，
进而被跳过或删除 —— 这是护栏失效的典型路径。

**由来**（2026-10-05，一天内四次同族实例）：

| # | 护栏 | 失效形态 | 若被误读的后果 |
|---|---|---|---|
| 1 | G1 文件计数 `echo "$FILES" \| wc -l` | 空输入返回 **1**（非 0） | 显性打印失效，读者以为真检了 1 个文件 |
| 2 | A-3 快照校验 `while read < <(grep ...)` | 空 manifest ⇒ 循环零次 ⇒ `failed=0` ⇒ **「校验通过」exit 0** | 防线对空输入假绿 |
| 3 | T1-P2 接线断言（未剥注释） | 注释掉调用仍 **11 pass / 0 fail** | 断言验的是注释里的字符串 |
| 4 | P1-1 模块图护栏（子进程无 try/catch） | 文件含无法解析 import ⇒ **子进程整体崩溃**，stderr 只回传代码帧，**丢失 `Could not resolve`** | 未来读者看到「输出不可解析」会以为护栏坏了 |

**核心判据**：**「护栏自身故障」与「被测对象故障」必须可区分。**
若二者产生同样的输出（如都表现为「输出异常」「无命中」「全绿」），
则护栏不可用 —— 因为它**无法告诉你它到底检没检**。

**实践要求**：
1. **空输入必须显式失败**（不是「无事发生」）：`if (${#items[@]} -eq 0) { echo "失败：无可校验条目"; exit 2; }`
2. **异常必须归类**：`try/catch` 包住可能抛异常的外部调用，
   把异常转成「带对象名 + 原因的失败记录」，而非让进程崩溃
3. **失败信息必须含对象标识**（哪个文件 / 哪条记录）与**原因**（不是只给代码帧）
4. **护栏的失败诊断质量是护栏价值的一部分** —— 验收护栏时，
   除「能抓到缺陷」外，还要验「**抓不到时能否说清为什么**」

**★ 反面示例（e111a6ad 的子进程）**：
```js
// 子进程脚本：Bun.build 在模块解析失败时抛异常（非 success:false）
for (const entry of files) {
    const built = await Bun.build({ ... });   // ← 抛异常 → 进程崩溃 → 诊断丢失
```
**修法**：
```js
for (const entry of files) {
    try {
        const built = await Bun.build({ ... });
        if (!built.success) { results.push(entry + "::BUILD_FAIL::" + built.logs.map(String).join(" | ").slice(0,200)); continue; }
        ...
    } catch (e) {
        results.push(entry + "::BUILD_FAIL::" + String(e?.message ?? e).slice(0, 200));
    }
}
```

### V9 ★ 断言的可靠性三族：注释免疫 / 锚点消失 / 失败路径不可诊断

**规则**：断言/护栏的**可靠性**不等于「它能抓到缺陷」，还要验
**「它在该红的时候是否一定红」**。三类失效模式（2026-10-05 全部实测）：

| 族 | 失效形态 | 实例 | 后果 |
|---|---|---|---|
| **① 注释免疫** | 断言匹配源码文本，注释满足 `toContain` / 注释掉调用仍匹配 | T1-P2：注释掉 `void tidyHeadlessCanvasIfNeeded()` → **11 pass / 0 fail**；<br>R4 superres：600 字符窗口**覆盖注释中的 `message.error` 字样**，删代码保留注释 → **反向断言仍绿** | 断言验的是注释里的字符串 |
| **② 锚点消失** | 断言依赖的字符串在回归时消失 ⇒ 空切片 ⇒ `not.toContain` 恒真 | R4 S-2：`panel.slice(panel.indexOf(锚点), end)` 锚点缺失 ⇒ `slice(-1, N)` 空串 → **1 pass / 0 fail** | **对最可能的回归形态无防护** |
| **③ 失败路径不可诊断** | 护栏崩溃/空输入时无法区分「护栏坏了」与「被测对象坏了」 | V8 四例（G1 计数 / A-3 空 manifest / P1-1 子进程崩溃） | 护栏被跳过或删除 |

**★ ①-a 亚形态：测试名过度声称**（2026-10-05 加入，三线独立指出）

**形态**：**测试名/描述承诺的性质 > 断言实际覆盖的范围**。
与 ① 本族（注释满足断言）**方向相反**：
| | 方向 | 机制 |
|---|---|---|
| **① 注释免疫** | 断言**太宽** | 被无关物（注释）满足 ⇒ 假绿 |
| **①-a 测试名过度声称** | 断言**太窄** | 承诺的一半没有断言覆盖 ⇒ 缺陷逃逸 |

**实例（同一文件内犯两次，故升级）**：
| # | 测试名承诺 | 断言实际 | 逃逸的缺陷 |
|---|---|---|---|
| 1 | 「二次注入不替换已安装实例」 | 仅 `navLog.length`（长度断言） | 幂等守卫移除后长度仍为 1 ⇒ **假绿**（B线 开发中自查发现，提交前改为**实例身份断言** `second === first`） |
| 2 | 「自检注入的假消息被清理（**不污染后续 dump**）」 | 仅 `body.children`（DOM 节点） | `msgLog` 残留自检记录 ⇒ **污染 dump**（测试线 b12r26 + 控制线 独立发现） |

**为什么危险**：**测试是绿的** —— 没人会去核对「测试名承诺」与「断言覆盖」是否一致。
缺陷逃逸后，测试名还会**反向误导**（读者以为该性质已被守护）。

**纪律**：
> **测试名里的每个承诺词，都应有对应断言**；
> 承诺词多于断言时主动警觉（尤其「不污染 X」「不重复 Y」「不影响 Z」这类**全称否定**表述）。

**修复方向**：**补断言追上测试名**（而非改测试名降级承诺）——
保持承诺、加强断言是更强的选择（R9 指出，本轮 `:171` 即如此修复）。

**★ ②「锚点消失」最隐蔽**（R4 P2 发现）：
- 它不是「断言写错」（写错会红），而是**「回归时会静默通过」**
- **危险点**：**最自然的回归写法恰好让锚点消失**
  ```
  修复后: if (prefillRequest && prefillRequest.id !== lastPrefillRequestIdRef.current) { ... }
  回归时: if (prefillRequest) { ... return; }        ← 锚点字符串消失
  ⇒ panel.indexOf(锚点) = -1
  ⇒ panel.slice(-1, N) = "" （长度 0）
  ⇒ expect("").not.toContain("return;") = 恒真 ⇒ 假绿
  ```
- **判据**：**若「恢复缺陷」会改变断言依赖的字符串，则该断言对回归无防护**

**★ 切片类断言的两条硬要求**（R4 两个 P2 归纳）：

> 源码文本切片断言（`slice` + `toContain`/`not.toContain`）必须满足：
> ① **锚点存在性前置断言**：`expect(idx).toBeGreaterThan(-1)`
> ② **断言前剥离注释**（`stripComments`）—— 否则注释中的字样会满足 `toContain`

| 来源 | 形态 | 假绿机制 | 触发条件 |
|---|---|---|---|
| R4 选项 C（S-2） | `slice(indexOf(锚点), indexOf(结束))` | 锚点缺失 → `-1` → **空串** → `not.toContain` 恒真 | **恢复缺陷写法**（锚点字符串消失） |
| R4 追加（superres） | `slice(ci, ci+600)` + `toContain` | 窗口**覆盖注释**中的同名字样 | **只删代码保留注释** |

**共同点**：都是「源码文本切片断言」在边界条件下失效，
且**触发条件都是最自然的回归写法** ⇒ 对真实回归无防护。

**实践要求**：
1. **切片/索引前断言锚点存在**：`expect(start).toBeGreaterThan(-1)`
2. **优先用「修复后必然存在」的结构做锚点**，避免用会被回归改写的字符串
3. **正反双向断言**：正向验新形态存在，反向验旧形态消失（但反向断言也要防锚点消失）
4. **验收断言时做「回归注入」而非「缺陷注入」**：
   前者是「把代码改回缺陷前的写法」（真实回归形态），
   后者是「人为破坏」（可能不是真实回归路径）
   ⇒ **两者都要做**，但**回归注入更能暴露 ② 族问题**

**★ 附1：证伪红数必须来自实测记录**（V7 补充）
报告写「实测 N 红」而非「恰好 N 红」—— 后者暗示精确但常凭记忆。
R4 实例：A线 自述「恰好 1 红」，实测 2 红（护栏更强，但自述偏保守）。

**★ 附1-a：证伪红数必须附【注入点】**（V7 附1 的扩展，2026-10-05 两次实测归纳）

**规则**：报告「注入 X → N 红」时，必须同时给出**注入位置**
（文件 + 行 + 注入形式：改函数体 / 改调用点 / 改常量 / 删分支）。

**为什么**：**同一注入意图在不同位置，红数不同** ——
不标注入点时，别人**复现不出你的红数**，会被误判为「你的数字不实」。

`expect(probeSource).toContain(anchor)` —— 关键词常量被改后，锚点消失，该断言变红。
**⇒ 这是 V9 ②（锚点守护）首次被证实「主动检测到锚点消失」**，

A线 报告的注入表红数，控制线复现时**两项对不上**：

本附条管「数字要可复现」（**可复现性**）——
**真测的数字仍可能不可复现**（本例），两者缺一不可。

> **函数体注入**验的是「实现逻辑对不对」；
> **调用点注入**验的是「接线对不对」——

**与附1-a 主体的关系**：主体管「红数可复现」；
本层管「**红数之外，注入点还决定能发现什么**」——
**同一个 0 红，在函数体注入下是「无缺口」，在调用点注入下是「有缺口」**。

**与附2 的关系**：附2 管**引用**（行号须附 commit 基准）；
本附条管**注入**（红数须附注入位置）——

**★ 附2：代码行号引用必须附 commit 基准**（V7 补充，2026-10-05 实测归纳）

**规则**：引用源码行号时写作 `路径:行号（@ commit）`，例如
`web/test/helpers/spa-navigation-probe.js:114（@ fdd4ea55）`。

**由来（本轮活例）**：控制线与 B线 就同一文件的三个行号产生分歧 ——
B线 引 `:81/:86/:95`，控制线"纠正"为 `:100/:105/:112`。实测三个版本：

| commit | MESSAGE_KEYWORDS | reset() | dump() | selfCheck() | 自检基线赋值<br>`var before = ...` |
|---|---|---|---|---|---|
| `78ae6c5b` | :37 | :81 | :86 | :94 | :95 |
| `fdd4ea55` | :56 | :100 | :105 | :113 | **:114** |
| `2aa59215` | :79 | :123 | :128 | :136 | :137 |

> ★ **口径修正（R9 P3-1，2026-10-05）**：原表第四列标题为「自检基线」，实际用的是
> **函数体首行** `var before = msgLog.length`，而前三列用的是 **`function`/`var` 定义行** ——
> **同一张表内两种口径**，读者可能误以为第四列指 `function selfCheck()` 行。
> 现拆为两列（定义行 + 赋值行）并显式标注，消除歧义。
> （R9 实测：`function selfCheck()` = 94/113/136，`var before` = 95/114/137，两行恒差 1。）

**⇒ 两个结论**：
1. **B线 的原引用在当时是准确的**（@78ae6c5b）—— 不是"引用错"而是"基准版本不同"
2. **控制线的"纠正"自身有偏差**：`:112` 是 `selfCheck` 的 JSDoc 结束行 `*/`，
   真正的基线赋值在 `:114`（**同行号在不同人眼里可差 2 行**）

**为什么这条重要**：不附基准时，**「引用错误」与「版本位移」不可区分** ——
分歧会被误判为「对方引用不实」，而实际双方都对。
同一文件在 3 个 commit 中行号位移 3 次（本例），位移是常态而非例外。

**与 V7 的关系**：V7 要求「报告断言逐条对码」，本条是其在**行号维度**的补充 ——
**没有基准的行号不是可对码的证据**。
（与「证伪红数须附注入点」同族：都是让证据**可复现**而非「看起来精确」。）

**★ 首个实例（2026-10-05，控制线自犯 + A线 独立复现）**：

本条纪律由 B线 于 2026-10-05 提出。**同一日**，控制线在 `75768505` 加的代码注释里写下：

**该数字在写下时是真的** —— 但它测的是**加断言前**的版本（`@9b4c8b85`）；
在**加断言后**（`@75768505` 起），Y 形态是 **1 红**。

A线 核实该注释时**复现不出 0 红**（实测 1 红），建隔离环境做两版本对照后定位：
| 版本 | Y 形态实测 | 含义 |
|---|---|---|
| `9b4c8b85`（加断言**前**） | **0 红** | 缺口存在（既有断言抓不住 Y 形态） |

未标基准时读者**无法判断注释在说哪一版**。

2. **连纪律提出者自己都自然犯** —— 说明这是**结构性问题**，非个人失误
3. **作者自己看不出来** —— 控制线提交后自检时未发现，是 A线 从「复现不出」反查才定位

**★ 附2-a：引用【未合并分支】的代码必须标注分支**（V7 附2 的扩展，2026-10-05 控制线自犯）

**规则**：引用源码位置时，若该代码**不在 main 上**，必须写成
`路径:行号（@ 分支 / commit）`，例如
`backend/internal/app/prompt_image_role.go:93（@ feat/f09-prompt-injection / 4a448e06）`。

**为什么附 commit 不够**：**对方树上可能根本没有这个文件** ——
此时「行号漂移」不是问题，「**文件不存在**」才是。

**实例（2026-10-05，控制线自犯）**：
控制线在给 B线 的裁定里写「后端 `applyImageRolePrompt` 因 `ProductImageCount <= 0`
直接 return（`prompt_image_role.go:93`）」——**未标分支**。
B线 在自己的树（`fix/w5-headless-reachability @ 1222f3cc`）里做了 4 项排除性检查：
```
ls backend/internal/app/prompt_image_role*.go     → 无
find backend -name "*image_role*"                 → 无
grep -rn "applyImageRolePrompt" backend/          → 空
grep -rn "输入图片角色清单" . --include="*.go"     → 空
```
⇒ 全部为空，B线 只能**回问「请确认引用来源」**，并列出 4 种可能解释请控制线裁定。

**代价**：B线 的 4 次搜索 + 一次回问往返；
若控制线标注分支，B线 可立即判断「该分支未合并 ⇒ 我不需要它」。

**★ 与 V7 附2 主体的区别**：
| | V7 附2 主体 | 附2-a |
|---|---|---|
| 场景 | 代码在**双方树上都有**，但**版本不同** | 代码**只在对方没有的分支上** |
| 失效形态 | 行号**指向错误位置**（静默） | 对方**搜不到**（显式，但浪费往返） |
| 修复 | 附 commit 基准 | 附**分支**（commit 不够） |

**★ 控制线自评**：这是**同日第二次自犯同族错误** ——
第一次是 V7 附2 首个实例（注释里的红数漏版本基准），
本日又犯附2-a。**⇒ 再次印证「连纪律提出者自己都自然犯」**，
且**自犯速度比落盘速度快**（两条纪律同日落盘、同日自犯）。

**★ 附2-b：引用行号必须用工具回显验证，不得目测计数**（测试线 2026-10-05 发现并复现根因）

**规则**：写下行号引用前，必须用 `grep -n` / `sed -n 'Np'` **回显验证**该行内容，
**不得**从无行号的输出中目测推算。

**实例（2026-10-05，测试线 自犯并自行复现根因）**：
测试线 执行 `sed -n '45,70p' prompt_image_role.go` ——
**`sed` 的输出不带行号**，然后靠目测数：
```

推算 45 + 10 - 1 = 54
但报告里写成了 :56   ← 目测计数误差 2 行
```
**控制线复核**：`grep -n` 给出 `54: if productImageCount > 0 {` / `57: } else {` ✓

**★ 与 V7 附2 主体/附2-a 的区别**（三种失效机制，同一族）：

| 形态 | 机制 | 引用者能否自知 |
|---|---|---|
| **附2 主体** | 版本不同 ⇒ 行号漂移 | 不能（需对比两版本） |
| **附2-a** | 代码在未合并分支 ⇒ 对方搜不到 | 不能（但对方会报） |
| **附2-b（本条）** | **同一版本内目测数错** | **不能**（连自己都以为是对的） |

**★ 为什么附2-b 最隐蔽**：前两者至少**双方基准不同**（可对比发现），
本条是**引用者自己算错且无从察觉** —— 除非用工具回显，否则**永远发现不了**。

**★ 三形态的「发现路径」维度**（测试线 2026-10-05 提出，控制线采纳）：

| 形态 | 谁能发现 | 何时发现 | 防线 |
|---|---|---|---|
| **附2 主体**（版本漂移） | **对方**（复现不出） | 对方执行时 | 附 commit 基准 |
| **附2-a**（未合并分支） | **对方**（搜不到） | 对方执行时 | 附分支 |
| **附2-b**（目测数错） | **只有自己** | **只在主动回显时** | **工具回显（唯一）** |

**⇒ 附2-b 是唯一「必须靠自查」的形态** ——
前两者对方会报（有外部检测点），附2-b **没有外部检测点**：
对方拿到的是一个「看起来正常」的行号，**不会觉得需要核实**。

**⇒ 这解释了为什么「工具回显」不是可选项而是唯一防线** ——
不是因为「更仔细就行」，而是因为**该失效模式没有任何外部信号**。

**★ 一般化**：判断一条纪律是否需要「工具化执行」，
可先问：**这个错误有没有外部检测点？**
- **有**（对方能发现）⇒ 靠协作可捕获，纪律提醒即可
- **无**（只有自己能发现）⇒ **必须工具化**，提醒无效

**★ 附2-c：断言「某物不可分发/不可用」前必须先试其反例路径**（控制线 2026-10-05 自犯）

**规则**：说「X **无法**做 Y」之前，必须**先试过让 X 做 Y 的那条路径**
（如强制选项、绕过开关），否则容易把「**默认不做**」说成「**做不到**」。

**实例（控制线自犯）**：
控制线对 B线 的 F-09 交付建议「把产出复制到入库路径」，理由是：
```

```
**★ B线 核实后反驳**：产物**已入库**（11 文件）——
```bash
$ git ls-files docs/artifacts/f09-channel-test/ | wc -l
11                                    ⇒ 已跟踪
$ git check-ignore -v .../RESULTS.md
exit=1                                ⇒ 未被忽略
```

**根因**：控制线的**前提正确但结论错误**：
| 推理步 | 判定 |
|---|---|
| `docs/artifacts/` 被 gitignore | ✓ 对（`.gitignore:5` 的 `docs/*` 通配） |
| ⇒ 产出**无法**通过 git 分发 | ✗ **错** —— **`git add -f` 可强制入库** |
| ⇒ 建议复制到入库路径 | ✗ 不必要 |

**★ 为什么这个错误特别值得记录**：
> **控制线自己在落盘纪律文档时，一直用的就是 `git add -f`** ——
> **它做的和它说的不一致**，却未察觉。

**⇒ 失效模式**：「默认行为」被当成「能力边界」。
**`-f` / `--force` / 绕过开关是常见的能力边界外路径** ——
断言「做不到」前先问：**有没有 force 路径？**

**★ 与 §四·五 的关系**：属**弱判据自检**族 ——
控制线做的是「**存在性检查**」（gitignore 里有这条规则 ⇒ 不可分发），
**而非「能力验证」**（试一下 `-f` 能不能加）。

**★ 一般化判据**：
```
断言「不可 X」前：
① 有没有 force / bypass 路径？（先试）
② 我自己的实践是否与我的断言矛盾？（自检）
```

**★ 附2-d：会变的对象必须重新取当前状态，不得用缓存观察**（测试线 2026-10-05 自犯）

**规则**：引用**会变化的对象**前，必须**重新取当前状态**，不得依赖先前的观察结果。

**会变的对象**（非穷举）：
```
文件内容（草稿 → 正式版）· 目录列表（新增/删除文件）

```

**★ 与 V7 附2 的关系（同机制，不同对象）**：
| | V7 附2 主体 | 本附条 |
|---|---|---|
| 对象 | **代码行号**随版本漂移 | **文件内容/目录/分支引用**随时间漂移 |
| 失效 | 引用者看到的是旧版本 | 引用者用的是旧观察 |
| 共同点 | **当时正确，之后失效** | **同上** |

**⇒ 本附条是 V7 附2 在「观察缓存」维度的扩展** ——
V7 附2 说「引用须附版本基准」，本附条说「**引用前须重取当前版本**」。

**★ 为什么比前几种更隐蔽**：前几种的观察**本身是错的**；
本附条的观察**当时是对的**（`RESULTS-DRAFT.md` 确实存在过）——
**失效发生在「观察」与「使用」之间的时间差里**。

**★ 可执行动作**：
```

□ 引用内容前：重新读（不用记忆中的内容）
□ 引用版本前：重新 rev-parse / git log

```

**★ 与 §四·五 的关系**：属**观测族** ——

此前成员管「观测**是否准确**」（位置/归属/覆盖/观测手段），

> ⇒ **一个通过率接近 100% 的判据，区分力接近 0。**
> 而判据② 的通过率取决于「版本是否已变」——
> 在快速迭代期（本轮 3 天 3 次行号位移），版本变化的概率很高 ⇒ 判据② 区分力强。

说明「只核可追溯」是**自然倾向**（判据① 更省力且几乎总通过），
**必须显式写成两项**才能对抗这种倾向。

**成本说明**（R10 自省）：判据① 读一遍注释即可；判据② 需**建树 + 注入 + 重跑**
（成本高一个量级）⇒ 这是「**成本驱动的不完整核验**」。

**与 V7 本体的关系**：V7 管「**不能凭记忆报数**」；本附条管「**不能凭来源判定数字有效**」。

## 四、协作纪律

### C1 ★ 读线状态必须翻到报告区

**规则**：读他线终端状态时，不得只看首屏（todo 列表）或尾部。
报告常出现在屏幕上方，`orca-ide terminal read` 默认只给当前屏。

**做法**：用大 `--limit` 翻读，或直接读该线落盘的报告文件。

**事故记录**：控制线两次漏读测试线状态——① 漏了配额阻塞报告（以为还在跑）
② 漏了 b12r20 归档报告（以为没回报）。

**★ 附：读脚本输出同样必须读到【汇总判定行】**（2026-10-05，控制线自犯）

**规则**：读工具/判据脚本的输出时，**不能只读中间的过程行**（如 `① ✓ ② ✓`），
必须读到**汇总判定行**（如「暂判【待定】」）与**退出码**。

**实例（控制线自犯）**：
控制线核验 F-09 判据脚本 H1 时，读到：
```

  ② 主元素方位: ref=左  out=左  ⇒ ✓ 通过
```
⇒ 得出「**H1 通过**」，并据此向 B线 与测试线 派单称「**H1 假绿**」。

**★ 实际输出还有第三行**（控制线没读）：
```
  判定：①② 通过；③ 待人工 ⇒ 暂判【待定】，人工补 ③ 后给最终结论
```
**⇒ 脚本是诚实的**（说「暂判待定」，退出码 2 = 须人工），
**控制线的「假绿」指控不成立** —— 是控制线**自己读了部分输出就下结论**。

**★ 与 C1 的关系**：C1 管**读终端**（不得只看首屏/尾部）；
本附条管**读脚本输出**（不得只读过程行）——
**对象不同、失效机制相同**：都是「取局部当全部」。

**★ 与 V9 ①-a 的关系**：

### C7 ★ 控制线的技术机制描述也要独立复核（可与 C6 合并适用）

**规则**：执行线在回报「控制线建议的坑」时，**机制描述与结论要分开验证**——
结论对不等于机制对，机制错会导致后续别处误用。

**事故记录**（2026-10-05，A线 报告 + 控制线独立复核）：

A线 报告：「`bun test` 进程内 `Bun.build` **不解析 tsconfig paths**；
`tsconfig` / `root` / `onResolve` 插件**三种配置均不生效**，而裸 bun 进程能解析」

**控制线实测复核**：

| 断言 | 实测结果 | 判定 |
|---|---|---|
| 进程内 Bun.build 解析失败 | `Could not resolve: "@/components/media-preview"` | ✅ 确证（逐字一致） |
| 裸 bun 子进程可解析 | `success=true` | ✅ 确证 |
| `tsconfig` 选项不生效 | 抛 `AggregateError: Bundle failed` | ✅ 确证 |
| `root` 选项不生效 | **时而 success=true、时而失败** | ⚠️ **不准确** |

**★ 真实机制（我的更正）**：不是「配置不生效」，而是
**「同一进程内首次 `Bun.build` 调用失败，后续调用成功」**（3/3 进程稳定复现）：
```
process 1: #1=THREW #2=true #3=true
process 2: #1=THREW #2=true #3=true
process 3: #1=THREW #2=true #3=true
```
⇒ 若只看单次探针（且该次恰好是第 2+ 次调用）会误以为「某配置生效」。

**为何这个差异重要**：
- A线 的**结论**（必须 spawn 子进程）**正确**——且理由更硬：子进程每次都是「首次调用」
- 但「三种配置均不生效」的**机制描述**会误导后续：别人可能以为「换个配置就能在进程内跑」，
  反复试错（实际是「首次必败」的时间性，与配置无关）

**★ 方法教训**：验证他人的实测结论时，要区分
**「结论正确」**与**「机制描述正确」**；后者需要**多进程/多轮采样**才能判定，
单次探针不足以区分「配置无效」与「首次调用失败」。

**派生纪律**：凡「某选项/配置不生效」这类断言，
报告必须给出**多轮采样证据**（至少 3 次独立进程），否则只能是「观察」而非「机制」。

| **工具** | V4 附2 | flaky 判定 → **多次独立进程**（非 `--rerun-each`） | §三 V4 |
| **溯源** | §四·五 溯源维度 | 「实测得到 X」→ **产出与其声称来源的绑定** | 本节（2026-10-05 新增） |

### 两个正交性质（评审线 R10 归纳）

```
生产侧：写的人要标基准（V7 附2 / V3 附）
审查侧：读的人要核基准（V7 附2 审查侧）
```
**⇒ 两侧缺一不可**：只做生产侧，过期数字仍会被采信（R10 实例）；
只做审查侧，则每次审查都要重新推导来源（成本不可持续）。

### 共同失效模式

| 模式 | 实例 |
|---|---|
| **表述强度 > 证据强度** | 「Y 形态 → 0 红」（漏版本基准，V7 附2 实例）；「2 次跑均未出现」（漏样本量，V4 附1 实例） |
| **弱判据冒充强判据** | 「可追溯」（通过率结构性接近 100%，区分力接近 0）被当成核验通过 |
| **成本驱动的不完整核验** | 判据② 需建树+注入+重跑，成本高一个量级 ⇒ 自然只做判据① |

### 使用方法（审计清单）

核验任何**引用数字/结论**的材料时，逐项自问：
```
□ 这个数字是在哪个 commit 上测的？（位置）
□ 证伪红数有没有标**注入点**？（位置-注入；同一意图不同位置红数不同）
□ 谁测的？谁修的？（归属）
□ 它承诺的性质，有多少被断言/证据覆盖？（覆盖）
□ 观测手段本身是否影响了被观测对象？（观测）
□ 阴性结论跑了多少次？（样本量）
□ flaky 判定用的是独立进程还是同进程重复？（工具）
□ 我做的「存在性检查」是否冒充了「逐条核验」？（弱判据自检）
□ 这份产出真的来自它声称的来源吗？绑定方法**曾检出过问题**吗？（溯源）
```

**★ 清单同时适用于自审**（测试线 2026-10-05 首次实战，用于自审 ENV-BASELINE）：

**理由**：自审与他审的盲区**不同** ——
| 场景 | 易犯 |
|---|---|
| **自审** | **弱判据自满**（材料来龙去脉自知 ⇒ 倾向跳过核验；「看到 ✓ 就完成」） |
| **审他方** | **成本驱动的不完整核验**（判据② 成本高一个量级 ⇒ 自然只做判据①） |
⇒ 两者互补，**同一份清单都要过**。

**★ 最后一项「弱判据自检」的由来**（第三次实例，测试线自审时发现）：
> 「如果我只做『有没有基准』的**存在性检查**（表里确实有 `f6236a18` 等 commit 字样），
> 就会判『有基准 ✓』而漏掉『**多数条目没有**』」

**⇒ 判据**：不是「表里**有没有**基准」，而是「**有几条**有基准 / **共几条**」。
**存在性检查是最自然的偷懒方式** —— 把它写成清单里的**具体自问句**比抽象规则更能防。

**★ 审计中的版本差陷阱**（A线 2026-10-05 指出，差点误报）：
核对「某物是否已消除」时，**必须先确认自己的树与文档基准的版本关系**。
A线 在本地 `a98e587e` 看到 `mock.module` 仍在，而 main 已清零 ——
**这不是「清零后又出现」，而是它的分支早于修复 commit**。
⇒ **不核版本就报告「我这边仍有」= 制造一个看起来是反例、实际是版本差的假警报。**

### ★ 溯源维度（第 8 维，2026-10-05 新增）

> **提出**：B线（F-09 渠道门交付时主动做全链溯源）；**核实**：测试线（独立复现）+ 控制线（独立复现）
> **裁定**：**不新设编号**，作为 §四·五 的**新维度**加入成员表。

**问的问题**（与已有维度互补）：
| 维度 | 问的问题 |
|---|---|
| 位置（V7附2） | 引用的行号是**哪个版本**的？ |
| 归属（V3附） | **谁**在**哪**测的？ |
| 覆盖（V9①-a） | 断言**覆盖**了承诺的范围吗？ |
| **溯源（本维）** | **这份产出真的来自它声称的来源吗？** |

**★ 为什么需要**：前 7 维管的都是「**同一份产出内部**」的可信度；
本维管「**产出与它的来源之间**」的绑定 ——
一份**内部自洽**的结论（判据可复算、数字可追溯）仍可能是**存错格的图**算出来的。

**实例（F-09 渠道门）**：
```
三方复算 H2③ 成立（B线 自测 + 测试线 复算 + 控制线 复现）
★ 但复算用的是【保存下来的图片文件】——
  若保存环节有误（存错图/存了别的格），复算会【一致地错】
```
**⇒ 测试线 明确声明了这个边界**（「验证了图→结论，未验证生成→图」），
**B线 随后补齐了那一跳**（taskId → resourceId → 下载 → hash 比对，9/9）。

**判据（可执行形式）**：
```
声称「实测得到 X」时，须能回答：
① 来源标识是什么？（taskId / runId / 命令 / 时间戳）
② 来源 → 产出的绑定方式是什么？（hash / resourceId / 像素比对 / 时间戳）
③ ★ 绑定方法【曾检出过问题】吗？（有检出能力的绑定才是证据）
```

**★ ③ 是本维最容易被跳过的一项**（与 V4 附1 同构）：
F-09 的溯源核验**首次跑时 A-S1 不匹配**（raw 曾被顺序实验覆盖），
修复后 9/9 通过 —— **「曾亮过一次」才证明这套核验不是走过场**。

**★ 有损变换会切断标识链**（本维的一个具体陷阱）：
```
DB 记录 515444 bytes（原始）→ B线 保存 155184 bytes（JPEG q88，~30%）
⇒ md5 链【必然断裂】（测试线 实测 0/9 不匹配）
⇒ 但【语义同一性】仍可验证（像素比对 MAD<3.3 ⇒ 9/9 同一图）
```
**⇒ 教训**：**交付物经过有损变换后，其「可溯源标识」会失效，
但「语义同一性」仍可验证 —— 核实者须知道该用哪个。**
⇒ 生产侧应在交付说明中**显式标注**「图片经重新编码」，
否则后续核实者会误判为「图不一致」（测试线 首次即踩此坑）。

**★ 本维的失效模式：恢复不全（B线 自犯，被本维核验抓到）**：

```
B线 跑顺序对照实验 → 覆盖了某格 -raw.png
实验后恢复：只恢复了【判定用的最终 PNG】
未恢复：    【溯源用的 raw】
⇒ 后续溯源核验暴露（A-S1 首次不匹配）
```

**规则**：
> **临时实验污染共享资源后，恢复必须覆盖【全部下游消费者的输入】，
> 而非只恢复【当前任务需要的那一个】。**

**★ 为什么容易犯**：
| 视角 | 需要的输入 |
|---|---|
| 实验者（当时） | 判定用的**最终图** |
| 核实者（未来） | 溯源用的 **raw** |
⇒ 两个输入集合**不相等** ⇒ 恢复漏项

**★ 与「单源纪律」（G4.1 附）互补**：
| 纪律 | 管什么 |
|---|---|
| 单源 | 一份数据**一个写者**（防并发写坏） |
| **本条** | 一份数据被写后，**恢复要恢复全链**（防单写者恢复不全） |

**★ 本维「③ 绑定方法曾检出过问题」的深层原则**（B线 指出，控制线认同）：
> **任何验证手段都必须先证明自己「能亮」—— 否则它的「通过」不构成证据。**

**同一原理的三个层次**：
| 层次 | 应用 |
|---|---|
| **判据层** | 判据必须先在 ground truth 上 PASS，才能判新生成（测试线 门规则） |
| **工具层** | 核验工具必须曾检出过问题，全绿才构成证据（本维 ③） |
| **断言层** | 锚点消失要能变红（V9 ② 锚点守护） |
⇒ 三者同源，**是「可证伪性」在三个对象上的体现**（判据 / 工具 / 断言）。

## V10 — 归因必须先核实身份（2026-10-06，A线实例 + 控制线裁定）

**触发**：A线 在 G4.1 事件报告中把执行 `git worktree add` 的进程归因为「控制线」，
实际是**评审线**。控制线用 `/proc` 环境变量核实后裁定：A线 归因错误。

**A线 的错误链**：
```
① 抓到 ps 输出（含 TRELLIS_CONTEXT_ID='pi_01a10788-...'）
② 但【没有比对】该 ID 与各线会话 ID
③ 凭【脚本内容】（"建修复批隔离树"、"把 A线 的未提交修复同步进隔离树"）
   推测是控制线（因为只有控制线会做复验调度）
④ 写入报告并投递
⇒ 这正是 C8 的同族错误（C8：投递前必须核实对方 handle 身份；
  本次：归因前必须核实对方 context ID）
```

**★ 正确的核实方法（本次实证有效）**：
```bash
# ① 抓进程时保留 context ID（不要只抓命令行）
ps aux | grep "[g]it worktree"

# ② 若有 PID，读 /proc/<pid>/environ 或父进程
tr '\0' '\n' < /proc/<pid>/environ | grep -E "TRELLIS_CONTEXT_ID|ORCA_TERMINAL_HANDLE"

# ③ 与各线已知 handle 对照（控制线 handle / 评审线 handle / 自己的 handle）
# ④ 前缀一致 ⇒ 同一会话；不一致 ⇒ 不是该线
```

**★ 为什么脚本内容不足以归因**：
- 脚本内容反映**意图**，不反映**执行者身份**
- 本次脚本含「把 A线 的未提交修复同步进隔离树」——听起来像控制线调度，
  但实际是评审线在准备复核（评审线也需要隔离树）
- **⇒ 身份只能由 ID 证明，不能由行为推测**

**★ 附带发现（同一事件）**：
1. **`git diff` 只能看到未暂存且未提交的改动**（★ 本条经 A线 二次自查修正）：
   评审线用 `git diff > patch` 导出「A线 的未提交修复」，得到 0 字节。
   **主因**：修复批 `40b9c915` 已在 **13:08:24** 提交，patch 生成于 **13:10:48**
   （晚 2 分 24 秒）⇒ 已提交内容 `git diff` 永远看不到 ⇒ 0 字节是**正常结果**，
   不是异常。控制线据此推断「A线 已提交」**正确**。
   **附带**：A线 的 journal 改动当时**已 `git add` 暂存**，同样不被 `git diff` 看到。
   ⇒ 导出他人工作状态时，按需选择：
      `git diff HEAD`（含暂存未提交）/ `git diff --cached`（仅暂存）/
      `git show <commit>`（已提交）/ 或直接以 commit 为隔离树起点。
2. **reflog 看不到失败的 commit**：控制线据 reflog 推断「A线 两次 commit 都成功」，
   但 A线 第一次 commit **失败**了（index.lock 被占），reflog 只记成功提交。
   ⇒ 判断「某次操作是否失败」不能只看 reflog，要看**操作方自己的输出**。
3. **同一目标被并发 worktree add 两次**：评审线先以 `9b80133d` 为起点建 `_f09fix`（13:09），
   后改以 `40b9c915` 为起点重建（13:12）—— 第二次会失败或需先 remove。
   ⇒ 多线共享仓库时，**隔离树路径也需先占用确认**（同 G4.1 的精神）。

**★ 纪律条款**：
- **V10-a**：报告归因（"X 线做了 Y"）前，必须用**进程身份**（context ID / handle）核实，
  不得凭脚本内容、时间邻近性或行为模式推测。
- **V10-b**：`git diff` 导出他人未提交改动时，用 `git diff HEAD`（含暂存区），
  否则会漏掉已暂存的改动。
- **V10-c**：判断某次 git 操作是否失败，以**操作方输出**为准，reflog 只反映成功状态。
- **V10-d**（控制线建议）：**隔离树的创建起点以 `.git/worktrees/<name>/logs/HEAD` 为准**，
  它比 `ps` 可靠（进程退出后不可查）。
- **V10-e**（★ A线 实验发现，2026-10-06）：**`git worktree remove` 会删除该 worktree 的
  reflog**。因此「reflog 无记录 X」**不能**证明「从未以 X 建过该树」，
  只能证明「**当前**这棵树的创建起点不是 X」。
  若需证明「曾以 X 建过」，须改用**管理目录时间戳**
  （`.git/worktrees/<name>/gitdir`、`commondir`、`logs` 的 mtime = 创建时刻）
  与进程启动时间对照，**或**在操作现场保留输出。

  **实验（2026-10-06，/tmp 隔离仓库）**：
  ```
  ① git worktree add --detach tree1 <C1>  ⇒ reflog 首行 = C1
  ② git worktree remove --force tree1     ⇒ .git/worktrees/tree1 目录【整体删除】（含 reflog）
  ③ git worktree add --detach tree1 <C2>  ⇒ reflog 首行 = C2，★ 无 C1 任何痕迹
  ⇒ 「reflog 无 C1」但 C1 确实建过 ⇒ 该证据不足以证明「未建过」
  ```
  **本实例应用**：`_f09fix` 的 reflog 首行 = `40b9c915`，但评审线确实先以 `9b80133d`
  建过同路径（PID 980725 的 ps 原文为证，含 context ID）。
  ⇒ 不能由 reflog 断言「那次失败」，只能断言「当前树的起点是 40b9c915」；
  而管理目录 mtime（13:13）**晚于** PID 980725 启动（13:09）
  ⇒ **最可能**是「先建的树被 remove 后重建」，但**未经操作方输出确认前应标为待确认**。
