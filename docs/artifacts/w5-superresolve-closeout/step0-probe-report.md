## 一、探针设计

控制线的核心问题：

> 当前 main 真机跑一次超分出图，钉死计费行为 ——
> 「**静默落 0.005 通配价**」还是「**干净报错**」？

**探针拆成两个对照场景**（比单跑一次更能钉死机制）：

| 场景 | 渠道配置 | 目的 |
|---|---|---|
| **A** | 有 `image_upscale` 精确档（777）+ 通配档（100） | 验证「精确档优先」是否生效 |
| **B** | **禁用精确档**，只留通配档（100） | 验证「无精确档时的兜底行为」 |

**为什么需要 B**：控制线担心的是「渠道没配超分档时会不会静默按通配价计费」——
只跑 A 无法回答这个问题。

**⇒ 渠道未配超分精确档时，任务照常创建、静默按通配档计价、不报错。**

## 三、结论

### 3.1 控制线的担忧：**成立**

**「静默落通配价」确实会发生** —— 当渠道没有 `image_upscale` 精确档时，
超分任务不会报错，而是**静默按通配档计价**。

**机制**（代码证据）：

```go
// backend/internal/app/model_router.go:375 matchSKUSelector
if expected == "" || expected == "*" {
    continue          // ← 通配档对任何 operation 都匹配
}
```

通配档（`selector_json = {}` 或含 `"*"`）**匹配一切请求**，
且 `channelModelPriceTierForIntent` 取「匹配分最高」的档 ——
无精确档时通配档以 score=0 胜出。

### 3.2 但「0.005」这个具体数值未复现

控制线提到「0.005 通配价」，实测环境里通配档是 **100 microcredits（= 0.0001 元）**，
不是 0.005。**0.005 可能来自生产环境的某个具体渠道配置**，本探针无法证实该数值。

**诚实边界**：探针证实的是**机制**（会静默落通配价），不是**特定金额**。

### 3.3 对本批任务 1 的直接支撑

**⇒ 管理端下拉缺 `image_upscale` 选项 = 运营无法配精确档 = 必然静默落通配价。**

这使任务 1（补下拉选项）从「完善度提升」升级为**缺陷修复** ——
不补这个选项，超分计费就**永远无法按超分定价**。
