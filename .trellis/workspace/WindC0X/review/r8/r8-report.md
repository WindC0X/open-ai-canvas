## §6 ★ 我的新发现：P3-1（纪律B 的前提无测试守护）

### 6.1 发现过程

我核验「若 `dump()` 语义改变，测试会红吗？」——做了两种注入：

| 注入形态 | 实现 | 结果 |
|---|---|---|
| **X：消费式增量** | `dump()` 返回后清空 `navLog`/`msgLog` | **1 红** |
| **Y：游标式增量** | `dump()` 返回 `slice(lastDumped)` 并推进游标，**不动内部数组** | **0 红** |

### 6.2 精确定位：既有测试守护的是「副本」而非「全量」

```ts
test("dump/reset 语义：dump 返回副本，reset 清空", () => {
    const snapshot = probe.dump();
    snapshot.navLog.push({ type: "fake", url: "/injected" });
    expect(probe.navLog, "dump 必须返回副本 —— 外部改动不得污染探针内部记录").toHaveLength(1);
    //     ^^^^^^^^^^^^^^^ 守护点：副本语义
});
```

**⇒ 既有测试守护的是「副本」**（`snapshot.navLog.push(...)` 不污染 `probe.navLog`）；
**「全量累计」语义无任何断言守护**。

### 6.3 后果

纪律B 的注释**依赖**「`dump()` 返回全量」这一事实：
> 「若不 reset，第 2 轮 `dump()` 会包含第 1 轮记录」

若未来有人把 `dump()` 改成**游标式增量**（形态 Y）：
- 全量测试**全绿**（0 红）
- 但纪律B 的注释**已过期**（此时不 reset 也不会污染，注释的警告变成误导）
- **反向风险**：若有人改成「增量 + 自动 reset」，纪律B 就变成「必须不 reset」的误导

### 6.4 建议（P3，不阻塞）

```
① 补一条断言守护「全量」语义（一行）：
   const a = probe.dump(); probe.dump();
   expect(probe.dump().navLog, "dump 必须是全量累计（纪律B 的前提）").toHaveLength(1);
② 或在纪律B 注释中标注「本纪律依赖 dump() 的全量语义，改语义需同步复核此注释」
```

**定级 P3**：当前无实际损失（语义未变），且注释已生效；属「**注释的事实前提无自动化守护**」的预防性建议。

### 7.1 ★ 自省一：我的例证错误暴露「跨文件举例时不核对路由归属」

**我的错误**：举了 `/tasks` 与 `/canvas/:id` 两个不同页面的消息，声称「可同页共现」。

这与 R6 教训十八（**跨序列对比必须按对象对齐**）**同族**：
- R6：跨序列按**序号**对齐 → 错配
- R8：跨文件按**关键词**对齐 → 错配

**教训二十**：
> **「同关键词」不等于「同场景」**。举例说明某个风险时，
> 必须核对**例证对象是否真的处于同一作用域**（同页/同路由/同生命周期），
> 否则例证不成立 —— 即使机制判断正确。

**同族延伸**：
```
R6 教训十八：跨序列对齐 ⇒ 按「对象 + 形态」而非「序号」
R8 教训二十：跨文件举例 ⇒ 按「同一作用域」而非「同一关键词」
共同点：**「相似」不等于「同一」**，必须核对承载关系（序列位置 / 路由归属）
```
