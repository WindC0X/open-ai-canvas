## §2 工具四类能力核验

### 2.1 导航记录（`pushState`/`replaceState` 包装）

```js
history.pushState = function (state, title, url) {
    recordNav("push", url);
    return originalPush.apply(this, arguments);   // ★ 透传
};
```

**核验**：
- ✅ 记录完整 query（`/canvas/abc?conversation=creation%3Alinear-flow-t1`）
- ✅ **透传**原方法（不吞掉真实导航）—— 我的注入：移除 `return originalPush.apply(...)` → **1 红** ✅

**★ 解决的真实问题**：SPA 内存路由中导航 URL 可能被**消费后立即改写**
（`project.tsx` 消费 `conversation` 后 `delete` + `replaceState`）——
事后读 `location.href` **已看不到原始导航目标**。探针把「每次真实导航调用」变成可回溯证据 ✓

### 2.2 消息捕获（`MutationObserver`）

**核验**：
- ✅ 关键词命中节点被捕获
- ✅ 非关键词节点**不**捕获（避免噪声淹没证据）
- ✅ `dump()` 返回**副本**（我的注入验证：外部改动不污染内部记录）
- ✅ `reset()` 清空

**★ 解决的真实问题**：antd `message` **数秒后自动消失** ——
「事后没看到警告」与「监视器失灵」**不可区分**（V8 纪律：失败路径必须与成功路径同等可诊断）✓

### 2.3 ★ 自检机制（核心承诺）

```js
function selfCheck() {
    var before = msgLog.length;
    var node = document.createElement("div");
    node.textContent = SELF_CHECK_TEXT;      // "未找到要接续的会话（探针自检，可忽略）"
    document.body.appendChild(node);
    return new Promise(function (resolve) {
        setTimeout(function () {
            var captured = msgLog.length > before;
            if (node.parentNode) node.parentNode.removeChild(node);   // ★ 清理
            resolve({ ok: captured, detail: captured ? "...可信" : "...无效" });
        }, 0);
    });
}
```

**我的独立证伪**（破坏关键词配置）：
```
注入：var MESSAGE_KEYWORDS = ["未找到", "会话"] → ["__broken__"]
结果：★ 4+ 红，含「★ 证伪：关键词配错 ⇒ 自检 ok === false」 ✅
```
**⇒ 自检机制真实有效**：它能区分「监视器活着」与「监视器失灵」✓

**✅ 额外核验**：自检节点**被清理**（`body.children` 长度 0）—— 不污染后续 `dump` ✓

## §5 ★ 坑5 的独立验证（本报告的核心发现）

### 5.1 缺口分析

```js
var MESSAGE_KEYWORDS = ["未找到", "会话"];
var SELF_CHECK_TEXT  = "未找到要接续的会话（探针自检，可忽略）";
```

**⇒ 自检消息用的正是探针自己的关键词** ⇒ 自检能验证的链条：
```
关键词配置正确 → 观察器安装成功 → 节点插入被捕获 → msgLog 记录 ✓
```

**但自检不能验证**：
```
目标警告的实际文案是否含这些关键词？    ← ★ 这是坑5 的实质
```

**反例场景**：若目标警告文案是「未检索到续接对话」，探针关键词 `["未找到","会话"]` **都不命中** ⇒
`selfCheck().ok === true`（监视器活着）但**目标警告从未被捕获** ⇒ **虚假阴性结论**。

### 5.2 控制线的使用纪律正好补这个缺口

**纪律第1条**：
> 先 grep 目标警告文案，确认含探针关键词（硬编码 `["未找到","会话"]`）

**我的独立验证**（对 R5 P2-1 的目标警告）：
```
目标文案（project.tsx:682）: 未找到要接续的会话，请从首页重新进入。
探针关键词: ["未找到", "会话"]
  → 含 "未找到"? True ✓
  → 含 "会话"?   True ✓
⇒ 命中 ⇒ 探针**可直接用于** R5 P2-1 的验证 ✓
```

**★ 且我核对了「需改关键词」的场景**：
```
tasks/index.tsx:357  message.info("该任务不是卡流程任务，未找到可打开的画布。")
  → 含 "未找到" ✓（但语义不同！「未找到可打开的画布」≠「未找到要接续的会话」）
tasks/index.tsx:382  message.warning("会话已保存在本机，云端同步尚未完成。")
  → 含 "会话" ✓（但这是成功路径的提示，非警告）
```

**⇒ 发现纪律第1条的细化空间**（见 §7 P3-1）：
仅 grep「是否含关键词」**不够** —— 还需确认**捕获到的消息是目标消息**（而非同关键词的其他消息）。
**建议**：阳性对照应断言**完整文案**或**关键片段**，不只断言「msgLog 非空」。

### 5.3 纪律第3条的正确性

> 阴性结论必须配 `selfCheck().ok === true` + **阳性对照**

**⇒ 这正是补坑5 的正确做法**：
- `selfCheck().ok === true` → 监视器活着（必要）
- **阳性对照**（构造一个**必然触发**的场景，确认探针**确实捕获到目标消息**）→ 监视器**看全了**（充分）

**⇒ 控制线的三条纪律是「必要 + 充分」的完整组合** ✓

## §7 发现

### P3-1：纪律第1条可细化（避免「同关键词不同消息」误判）

**现状**：纪律第1条 = 「先 grep 目标警告文案，确认含探针关键词」

**我发现的边界**：探针按**子串**匹配，若页面存在**其他含相同关键词的消息**，
阳性对照可能捕获到**非目标消息**却判定为「探针工作正常」。

**实例**（我核实的）：
```
"该任务不是卡流程任务，未找到可打开的画布。"   ← 含 "未找到"
"未找到要接续的会话，请从首页重新进入。"        ← 目标消息（同含 "未找到"）
```
若两者在同一页面同时出现，`msgLog` 会包含两条 —— 断言「msgLog 非空」无法区分。

**建议**（不影响本批使用）：
> 阳性对照应断言**完整文案**或**关键片段**（如 `msgLog.some(m => m.includes("要接续的会话"))`），
> 而非仅「msgLog 长度 > 0」；并建议在 `dump()` 结果中保留**原始文案**（当前已 `slice(0, 200)`，够用）。

**定级 P3**（工具使用纪律的细化，非代码缺陷；当前目标场景无冲突）。

### ✅ 无 P0/P1/P2
