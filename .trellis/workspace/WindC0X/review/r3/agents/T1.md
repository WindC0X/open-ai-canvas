## 重点① 逐字段核对：`applyHeadlessTidyPositions` 是否真只投影 position

**结论：断言成立**（除下文 F3 的调用方快照竞态外，机制本身无 metadata 泄漏）。

- `web/src/lib/canvas/headless-tidy.ts:58-61`：`nodes.map((node) => (pending.has(node.id) && positions.has(node.id) ? { ...node, position: positions.get(node.id)! } : node))`
  - 唯一写入字段是 `position`；`metadata` 走 spread **按引用复制**，无就地写入、无 `Object.assign`、无 `delete`；
  - 不在批次内 / 不在坐标表内的节点返回**同一引用**（不产生无谓渲染）；
  - `positions` 由 `layoutCanvasAuto` 生成，值形如 `{ x, y }`，不含 `metadata`/`status`/生成参数键。
- 反例构造（源对象 metadata 带任务态）：测试 `web/test/task-face-workspace-type.test.ts:96-116` 已构造 `generationTaskId/prompt/status/model/size`，断言 `next[0].metadata).toBe(nodes[0].metadata)`（同引用）且 `{position: _before, ...beforeRest}` 与 after 逐字段相等 → **测试有效且非镜像实现**（它断的是结构不变式，不是复述实现分支）。我另核对 `setNodes` 调用点（`use-canvas-project-lifecycle.ts:174`）回调内**只**调用该函数，未追加任何 metadata 写入。
- 与 `layoutCanvasAuto` 的**上游**契约无污染：该函数只读 `position/width/height/type/metadata.locked` 并返回坐标 Map（`web/src/lib/canvas/canvas-layout.ts:136-142`）。

→ 设计卡反模式 A5「整理不触碰任务态」在**函数级**有代码结构防线，成立。

### [P2] 首入标记早写于整理完成 ⇒ 中断后永久跳过整理
- 文件：`web/src/pages/canvas/use-canvas-project-lifecycle.ts:169`
- 证据：
  ```ts
  168  const batches = planHeadlessTidyBatches(current.nodes, current.connections, 6);
  169  markHeadlessCanvasTidied(projectId);      // ← 先落标记
  170  if (!batches.length) return;
  172  const positions = layoutCanvasAuto(...);
  173  for (const batch of batches) {
  174      if (isStale()) return;                // ← 中途退出，标记已落
  175      setNodes(...); await 16ms;
  ```
- 影响：标记注释语义是「每个画布只整理一次」（`headless-tidy.ts:24`），实际语义是「尝试一次」。用户在 16ms×N 帧窗口内切走画布/触发 stale → 整理半途而废且**永不重试**；headless 画布的初始排布恰是「乱」的，用户会看到一半整齐一半乱且无法自愈。
- 建议：把 `markHeadlessCanvasTidied` 移到循环正常结束后（或仅在 `batches` 全部提交且 `!isStale()` 时写入）。

### [P2] 整理用「标记前的快照坐标」覆盖实时 store ⇒ 窗口内用户编辑的 position 会被静默回写（机制成立，当前被 F1 挡住不可达）
- 文件：`web/src/pages/canvas/use-canvas-project-lifecycle.ts:168,172,174`
- 证据：`batches` 与 `positions` 都基于第 168 行 `current.nodes` 快照；第 174 行以**函数式更新**读实时 `nodes`，却用快照坐标写 `position`：`applyHeadlessTidyPositions(nodes, positions, batch)`。`applyHeadlessTidyPositions` 只做 `positions.has(id)` 判定，**不校验节点是否已被移动/删除**；`planHeadlessTidyBatches` 的 locked 过滤发生在 168 行（快照时点），窗口内新拖动的节点不会被排除。
- 影响：整理期间（数十到数百 ms）的用户拖拽结果被旧坐标覆盖；`metadata` 不受影响（故不触发任务重跑，与重点① 的结论不冲突）。当前因 workspaceType 无写入者不可达；**F1 一旦修复，此竞态立刻变成真实缺陷**。
- 建议：批提交前用 `revision`/内容哈希校验快照未过期，或对 batch 内节点加「自整理开始未被移动」判定；最省事的做法是整理期间 `readOnly`/忽略画布 pointer 事件并在结束后释放。

### [P2] 候选集筛选规则三处漂移（Frame 节点）
- 文件：`web/src/lib/canvas/headless-tidy.ts:41`、`web/src/pages/canvas/use-canvas-project-lifecycle.ts:172` vs `web/src/lib/canvas/canvas-layout.ts:137`
- 证据：
  - `planHeadlessTidyBatches`：`!node.metadata?.locked && !node.parentId`
  - 调用方重算 `positions` 时：同样只滤 locked/parentId
  - `layoutCanvasAuto`：`!node.metadata?.locked && node.type !== CanvasNodeType.Frame`
- 影响：无 `locked` 的 Frame 节点会进入 candidates 并被分进批次，但 `layoutCanvasAuto` 的返回 Map 里没有它的坐标 → 该节点所在帧整帧空转（`positions.has` 兜底，不出错坐标），且占掉 `batchSize=6` 的名额，流式批次数虚增。三处规则漂移在未来改筛选条件时会产生静默不一致。
- 建议：抽一个共享谓词（含 Frame 条件），`planHeadlessTidyBatches`、`layoutCanvasAuto` 与调用方共用；调用方应直接复用 plan 返回的 `positions`（现在重算一次属冗余）。

### [P3] 后端不校验枚举值 + 前端 `as never` 强制转换 ⇒ 类型声明边界宽于运行时保证
- 文件：`backend/internal/canvas/user_data_page.go:82`、`web/src/lib/canvas/headless-tidy.ts:26`

### [P3] 下载文件名扩展名判定脆弱（MIME 子串匹配 + 回退分支丢失 mediaType）
- 文件：`web/src/lib/task-face-download.ts:41-46`、`:68-75`
- 证据：`if (mimeType.includes(mime.split("/")[1]))` —— 子串匹配会把 `video/mpeg` 判成 `mp4`；走 `previewUrl` 回退分支时 `kind` 只来自 `task.previewKind`（枚举仅 `image|video`），audio 任务回退下载会拿到 `.mp4/.png`。
- 影响：仅文件名扩展名与真实媒体不符（字节内容正确、无数据丢失），用户双击可能用错应用打开。未构造真实 audio 回退用例验证，属静态推演。
- 建议：扩展名以 `taskDeliverableOutput(task)?.mediaType` 为主判据，MIME 仅做细化；回退分支同样按 `output.mediaType` 定扩展名。
